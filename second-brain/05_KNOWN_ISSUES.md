# 05 - Known Issues & Risks

## Current Bugs
- None in application code (Phases 0 through 13 complete, 107/107 tests passing, verified clean in a freshly-migrated environment, re-confirmed by a final adversarial red-team pass). One **test-infrastructure** bug is open — see "Phase 9 … `db_session` fixture leaks committed data" below.
- The backend still emits timezone-naive timestamps for DB-read values (Phase 11 note 1) — worked around client-side, not fixed at source. Most impactful remaining code-level item.

## Final red-team audit (2026-08-24) — resolved
1. **Two real test-coverage gaps, both closed.** No test exercised an *expired* JWT specifically (only a missing token or wrong password) — the `ExpiredSignatureError` branch in `app/core/security.py::decode_access_token` had zero coverage. And no test proved job durability across a "backend restart" — architecturally sound (workers are stateless pollers, all state lives in the DB) but never actually demonstrated. Added `tests/test_auth.py::test_expired_token_rejected` and `tests/test_e2e.py::test_e2e_backend_restart_with_pending_jobs`; both pass.

## Final red-team audit — found, NOT fixed (documented reasoning)
1. **Zero git commits.** `git log` reports "does not have any commits yet" — the entire repository is untracked working-tree content. Not fixed: creating commits requires the user's explicit instruction (per operating guidelines), not something to do unprompted during an audit. This matters for submission: a zip of the working directory still satisfies deliverable #1, but there is no commit history to inspect.
2. **SQLite never enables `PRAGMA foreign_keys=ON`.** FK constraints are declared in every model but not enforced by the SQLite engine used for local dev/tests (PostgreSQL, the production target, always enforces them). Checked whether this has any actual effect: the only two hard-delete call sites in the codebase (`DoctorWorkingHours` bulk delete, single `DoctorLeave` delete) operate on rows with no FK-dependent children, so there is no demonstrated orphan-row or cascade-delete bug today. Left as-is rather than risk the 107-test suite for a parity-only, currently-inert fix.

## Phase 13 (final audit) — resolved
1. **CRITICAL — privilege escalation via self-registration.** `POST /auth/register` accepted a caller-supplied `role` field with no restriction: any unauthenticated request with `{"role": "ADMIN", ...}` received a fully-privileged admin account (verified empirically — a raw `curl` got a 201 with `role: ADMIN`, no auth token involved). This directly contradicted AGENT_SPEC's "Admin creates and manages doctor profiles" model and Phase 3's own security requirement #6 ("admin-only operations must be protected"). Nearly every test file's setup helper depended on this exact behavior to bootstrap admin fixtures (9 files), so the fix is a settings flag (`ALLOW_PRIVILEGED_SELF_REGISTRATION`, default `False`) rather than a blanket restriction — see decision 26. Regression test: `tests/test_auth.py::test_privileged_self_registration_rejected_by_default`, which explicitly flips the flag back to its secure default and confirms ADMIN/DOCTOR self-registration is rejected (403) while PATIENT registration still works.
2. **CORS misconfiguration.** `allow_origins=["*"]` combined with `allow_credentials=True` — a real, flaggable misconfiguration even though this app's Bearer-token auth never actually relies on cookies/credentialed requests. Fixed: explicit `CORS_ALLOWED_ORIGINS` allow-list, `allow_credentials=False`. See decision 27.
3. **No root `.gitignore` existed anywhere in the repo** (only `.venv/.gitignore` and `frontend/.gitignore`) — `backend/.env`, `backend/healthcare_dev.db`, `__pycache__/`, `.pytest_cache/` were all one `git add -A` away from being committed. Added a root `.gitignore` covering env files, Python/Node artifacts, and local DB files.
4. **Documentation drift in `docs/architecture.md`.** The "Backend Module Structure" and "Frontend Structure" sections still described the Phase 0 *plan* (e.g. `models/consultation.py`, `models/ai_summary.py`, `workers/hold_expiry_worker.py`, none of which exist — the real files are `models/clinical.py`, no separate hold-expiry worker) rather than what was actually built. Regenerated both sections from the real file tree.

## Resolved 2026-08-23 (Phase 6 hardening pass)
1. **No real database-level double-booking constraint.** Previously the only protection was a Python `threading.Lock` (in-process only) plus `SELECT FOR UPDATE` (a no-op on SQLite). Added a partial unique index `uq_doctor_profile_start_time_active` on `appointments(doctor_profile_id, start_time)` WHERE `status IN ('HELD','CONFIRMED','RESCHEDULED')` (migration `f39781a8abe6`, applied on top of `bcd7ea881066`). `appointment_repository.create()` and `.reschedule()` now catch the resulting `IntegrityError` and translate it into a `ConflictError` (409). Verified with a new test (`test_appointment_double_booking_db_constraint`) that inserts two conflicting rows directly, bypassing the application-level lock entirely, and confirms the DB rejects the second one.
2. **Hold-confirmation booking path had no concurrency guard at all.** The `hold_id` branch of `AppointmentService.create_appointment` never acquired `_booking_lock` (only the direct-slot-booking branch did), and `with_for_update` is skipped on SQLite — so on SQLite this path was completely unprotected. Now wrapped in the same `_booking_lock` as the direct-booking path.
3. **Missing regression test for expired-hold booking.** Phase 6's spec explicitly required an "expired hold" appointment test; only Phase 5's hold-layer test existed. Added `test_expired_hold_cannot_be_confirmed_into_appointment`, which expires a hold directly in the DB and confirms booking through it is rejected (422) and the slot remains bookable by someone else.
4. **No assertion that reschedule doesn't duplicate a row.** Added a count check to `test_reschedule_appointment_and_reschedule_to_unavailable_slot` confirming the patient still has exactly one appointment after rescheduling.
5. **Confusing FK naming collision.** `Appointment.doctor_id` → `users.id` (doctor's user account) but `AppointmentHold.doctor_id` → `doctors.id` (doctor profile) — same attribute name, different target tables. Given a full rename would touch the public API response schema (`HoldResponse.doctor_id`) and ripple across ~8 files for a naming-clarity issue rather than a proven bug, only added explicit clarifying comments on both model columns rather than renaming. **Still open if a full rename is wanted** — flag before Phase 9+ builds more code that could inherit the confusion.

## Phase 12 (integration/E2E) — resolved & notes
**Resolved:**
1. **Reschedule created no notifications at all.** `AppointmentService.reschedule_appointment` synced the calendar but never queued a notification, so neither party was told the appointment had moved — a requirement of Phase 12's RESCHEDULE workflow. Now queues a `BOOKING_CONFIRMATION` for the new time to patient + doctor and re-arms the reminder. Regression test: `test_e2e_reschedule_workflow`.
2. **Stale reminders survived reschedule and cancellation.** A reminder queued for the original time stayed PENDING and would have been delivered after the appointment moved or was cancelled (this was the Phase 9 open item #2). Both paths now call `notification_service.supersede_pending_notifications(...)` first. Regression tests: `test_e2e_reschedule_workflow`, `test_e2e_cancellation_workflow`.

**Notes:**
3. **E2E tests must use scoped assertions.** The workers process *every* due row in the shared test DB, so other tests' rows land in the same in-memory provider. Two E2E tests initially failed in the full suite while passing alone, for exactly this reason. `assert_events_exist_for()` in `tests/test_e2e.py` is the pattern to copy — assert on this appointment's ids, never on a provider's total size. Root cause is still the `db_session` fixture leak below.
4. **The 100-thread concurrency case stays in `test_concurrency.py`.** `test_e2e_failure_simultaneous_booking_attempts` covers the integration-level outcome (loser gets a clean 409 and creates no partial state), not thread contention.

## Phase 11 (frontend) — notes
1. **Backend emits timezone-naive timestamps for DB-read values — worked around in the frontend, root cause still open.** Values built in memory (generated slots) serialise as `...+00:00`, but anything read back from the database serialises with no timezone designator (`2026-08-31T11:00:00`). JS parses the latter as *local* time, which shifted every hold/appointment by the viewer's UTC offset — holds appeared pre-expired and unbookable. **Found by driving the real UI, not by the build passing.** Frontend fix: `parseServerDate()` in `src/lib/format.ts` treats a missing designator as UTC. The cleaner fix is backend-side (make the DB layer return tz-aware datetimes so every client gets unambiguous ISO-8601) — worth doing in Phase 12/13; until then any *new* API consumer will hit the same trap.
2. **No automated frontend tests.** Phase 11 doesn't require them and none were added. Verification was manual browser-driven (see `04_TEST_STATUS.md` for exactly what was exercised). A future phase wanting regression safety on the UI would need Vitest + Testing Library, or Playwright for the full flows.
3. **Expected 404s appear in the browser console.** The appointment detail pages probe `GET .../ai/pre-visit-summary`, `.../ai/post-visit-summary`, and `.../consultation`, which legitimately 404 before those exist; the calls are `.catch(() => null)`-wrapped and render proper empty states. The console noise is cosmetic, not a failure.
4. **`npx` is broken in this repo path on Windows** because the directory name contains `&` — run local binaries directly (`node ./node_modules/vite/bin/vite.js`). Noted in `frontend/README.md`. Affects tooling only, not the app.
5. **Removing a leave date does not un-conflict appointments.** The admin UI states this explicitly in the confirm dialog. Matches backend behaviour (Phase 8 never implemented restoration) — flagged so it isn't mistaken for a UI bug.

## Phase 10 (Google Calendar) — notes
1. **`GoogleCalendarProvider` never verified against the live Google Calendar API.** Only `MockCalendarProvider` and injected test doubles are exercised by the suite — no Google Cloud project / OAuth credentials in this environment. The OAuth refresh-token exchange, the `id`-supplied-on-create idempotency behaviour (relies on Google returning 409 for a duplicate id), and the API request shapes are all written to Google's documented v3 contract but **unverified end-to-end**. Same caveat class as Phase 7's `RealAIProvider` and Phase 9's `RealEmailProvider`. Must be checked before claiming production readiness (Phase 13). Setup steps are in `docs/google-calendar-setup.md`.
2. **Google event ids have a character-set restriction that `idempotency_key` satisfies only incidentally.** Google requires custom event ids to be base32hex (lowercase `a-v`, digits `0-9`, length 5–1024). `uuid4().hex` is `0-9a-f`, which is inside that set, so it is valid — but nothing enforces this if the key generator is ever changed. Worth an explicit validator/comment if that code is touched.
3. **Doctor-leave conflicts do not currently sync to the calendar.** When `DoctorLeaveService` marks appointments `CONFLICTED`, it queues a patient notification (Phase 8) but does not arm a calendar DELETE/UPDATE for those appointments' events — so a conflicted appointment can remain on the calendar. Not in Phase 10's stated scope (which specifies create-on-booking / update-on-reschedule / delete-on-cancellation only), so deliberately not built. Worth wiring in Phase 12's integration pass.
4. **`MockCalendarProvider` is instantiated fresh per `get_calendar_provider()` call**, so its in-memory event store does not persist across calls in DEMO_MODE at runtime (tests inject one shared instance instead). Fine for demo purposes — the durable state that matters lives in the `calendar_events` table — but means a DEMO_MODE run can't be introspected for "what's on the mock calendar" across requests.

## Phase 9 (notifications) — important, still open
1. **`tests/conftest.py`'s `db_session` fixture leaks committed data across tests — discovered, NOT fixed.** The fixture wraps each test in `connection.begin()` + `transaction.rollback()` at teardown, but code-under-test commits many times per test (every repository call does `db.commit()`). Only the *last* still-open commit boundary gets rolled back at teardown; every earlier `commit()` in the same test is durably written to the shared in-memory SQLite DB and survives into later tests. This was invisible before Phase 9 because no test asserted an unscoped/whole-table count; Phase 9's notification-job creation (many more commits per request) made it visible via `db_session.query(NotificationJob).count() == 0`-style assertions failing depending on run order.
   - **Attempted fix:** the standard SQLAlchemy SAVEPOINT/`begin_nested()` + `after_transaction_end` event-listener pattern. It did **not** stop the leak (still observed leaked rows) and additionally broke `test_concurrency.py` (which manages its own sessions via `TestingSessionLocal()` bound directly to `test_engine`, bypassing this fixture's connection — the two didn't compose). Reverted.
   - **Current mitigation:** Phase 8's and Phase 9's own tests were rewritten to be leak-tolerant (before/after count deltas instead of absolute counts; scoping worker-processing assertions to specific job IDs/appointment IDs instead of trusting aggregate batch stats). All 76 tests pass, twice in a row.
   - **Still needs a real fix.** A future pass should either (a) get the SAVEPOINT pattern working correctly with SQLite's savepoint quirks and reconcile it with `test_concurrency.py`'s separate session-management approach, or (b) switch the test DB to a per-test throwaway SQLite file/schema instead of one shared in-memory DB for the whole run. Until then, **any new test asserting an absolute/unscoped count across a shared table is at risk** — prefer scoped or delta-based assertions.

## Phase 9 (notifications) — other notes
1. **`RealEmailProvider` never verified against a live SMTP server.** Only `MockEmailProvider` and injected test-double providers have been exercised by the test suite — no SMTP credentials/server available in this environment. Same caveat as Phase 7's `RealAIProvider`.
2. **Stale reminder jobs are not cancelled when an appointment is cancelled or rescheduled.** An `APPOINTMENT_REMINDER` job scheduled at booking time will still fire later even if the appointment was cancelled in the meantime (`process_job` doesn't re-check appointment status before sending). Deliberately not built — no `SKIPPED`/cancelled state exists in the `NotificationStatus` enum, and adding one is a bigger change than this phase's scope. A future phase could add a status check in `NotificationService._build_content` or have `cancel_appointment` mark pending reminder jobs FAILED with a "superseded" reason.
3. **Booking-notification queueing runs as a separate commit after the appointment's own commit** (not inside the same transaction) — deliberate (see decision 14), but means there's a narrow theoretical window where an appointment commits successfully and the process crashes before the notification-queueing commit. Acceptable: notification job creation is a simple DB insert immediately after a DB write that just succeeded, and the whole point of requirement 1 is that this exact scenario doesn't corrupt the appointment.

## Phase 8 (doctor leave conflicts) — notes
1. **Pre-existing, unrelated bug noticed but NOT fixed (out of Phase 8 scope):** `GET /appointments?doctor_id=...` (admin listing, `appointment_repository.list_for_doctor`) filters on `Appointment.doctor_id` (the doctor's **user** id), but every other doctor-scoped endpoint/query in the codebase (schedule, leave, slots, conflict detection) uses the doctor **profile** id (`doctors.id` / `Appointment.doctor_profile_id`). Passing the profile id most callers would naturally have (e.g. from `POST /admin/doctors`) into that query param silently returns zero results. Phase 8's own admin-inspection test (`test_admin_can_inspect_conflicted_appointments`) sidesteps this by filtering on `status=CONFLICTED` alone, without `doctor_id`. Flagging for a future phase — likely ties into the `Appointment.doctor_id` vs `AppointmentHold.doctor_id` naming-collision issue already recorded above.
2. **Leave creation does not touch `AppointmentHold` rows.** Only *appointments* (HELD/CONFIRMED/RESCHEDULED) are marked CONFLICTED, matching the spec's literal wording ("find all existing appointments overlapping the leave"). An active hold on that date/doctor is left alone — it will simply fail its own overlap/boundary re-check on confirmation (Phase 6 logic) or expire on its own TTL (Phase 5), and slot generation for that date already excludes leave days. Not treated as a bug, just documenting the boundary.

## Phase 7 (AI subsystem) — still open
1. **`RealAIProvider` never verified against a live LLM endpoint.** Only `MockAIProvider` (DEMO_MODE) and injected test-double providers have been exercised by the test suite — there is no API key / real LLM instance in this environment. The HTTP call shape (OpenAI-compatible `/chat/completions`, `response_format: json_object`) is standard but unverified end-to-end. Must be checked against a real provider (or a documented compatible one) before claiming production readiness.
2. **No retry/backoff on the AI call itself.** A single transient timeout produces one `FAILED` AISummary row; the only "retry" path is the caller hitting the generate endpoint again. This matches the spec's requirement that "a retry/fallback path exists" (the endpoint itself is that path), but there's no automatic retry — worth revisiting if Phase 9's background worker pattern should also cover AI retries, not just notifications.
3. **No rate limiting or cost guard on AI generation endpoints.** A patient or doctor can call the generate endpoints repeatedly, each one making a real (billed, if not DEMO_MODE) LLM call. Out of scope for Phase 7 per the spec, but worth flagging before production.

## Identified Risks & Technical Considerations (still open)
1. **Never verified against real PostgreSQL.** All tests still run against SQLite; the `SELECT FOR UPDATE` code path in `appointment_repository.py` has effectively 0% real coverage (it's a no-op on SQLite by design — see `with_for_update` guard). The new DB-level unique index (see above) is dialect-agnostic and should hold identically on Postgres, but this has not been executed against a live PostgreSQL instance — no such instance is available in this environment. Must be verified before claiming production readiness (Phase 13 audit).
2. **The 100-simultaneous-booking test doesn't exercise real concurrency.** `test_concurrency.py` wraps the entire DB session lifetime in a single `threading.Lock` (`_db_session_lock`) because SQLite's `StaticPool` shares one connection and cannot handle true concurrent access from multiple threads — this fully serializes the "concurrent" requests. The test now has a second, independent line of defense (the DB unique constraint, see Resolved #1) but the test itself still can't prove true concurrent-DB-write safety without a real multi-connection database (e.g. Postgres) in the test loop.
3. **Hold Expiry Race Conditions:** `synchronize_session=False` and `ensure_utc` helper implemented in Phase 5 to prevent ORM evaluator type mismatches and hold expiry race conditions.
4. **External Provider Resilience (Phase 7-10):** Provider calls must remain strictly outside DB transaction boundaries to avoid long-held locks during HTTP timeouts.

## Technical Debt & Reminders
- Keep API route handlers thin — delegate all business rules to services (`DoctorService`, `ScheduleService`, `LeaveService`, `SlotService`, `HoldService`).
- Never hardcode secrets — pull strictly from Pydantic `BaseSettings` / environment variables.
- Maintain `DEMO_MODE` capability with zero external API dependencies.
